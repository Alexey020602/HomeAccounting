Это приложение задумывалось как обучающее для освоения современных подходов разработки на C#.

Задача приложения - учет и анализ бюджета.
Пользователь фиксирует трату на основе данных чека или введенных вручную данных в рамках одного из бюджетов, в которых он принимает участие. 

Я собираюсь развивать проект с оглядкой на [репозиторий с эволюцией архитектуры](https://github.com/evolutionary-architecture/evolutionary-architecture-by-example) в качестве примера.

### Краткая вводная по истории проекта

Я начал делать приложение как модульный монолит. Из-за этого я столкнулся с трудностями с разделением на слои и Bounded Contexts. Поэтому после изучения [репозитория с эволюцией архитектуры](https://github.com/evolutionary-architecture/evolutionary-architecture-by-example) я нначал переписывать проект под один проект, как в Chapter 1 в примере.

Поэтому сейчас сложилась следующая картина. Проекты AppHost, ServiceDefaults, HomeAccounting, HomeAccounting.Tests, ClientServerShared, ClientServerContracts, Client и BlazorConsolidated являются актуальными, с которыми я работаю. Остальные проекты остались от этапа с модульным монолитом, и после воспроизведения всей логики в проекте MyBudgets я их удалю.

### Модель данных

Основной сущностью является `бюджет` (Budget). Он обладает следующими свойствами:
- Название
- День месяца, с которого начинается расчетный период (например день выплаты зарплаты)
- Ограничение по расходам
- Пользователь, создавший бюджет
- Дата создания бюджета
- Пользователи, участвующие в бюджете
- Траты в рамках данного бюджета

`Трата` (Spending) обладает свойствами:
- Дата покупки
- Дата добавления
- Сумма
- Описание

`Траты` могут быть двух типов `Трата на основе чека` (ReceiptSpending) и `Трата, добавленная вручную` (ManualSpending). `Трата, добавленная вручную` просто хранит вручную введенные `сумму` и `описание`. `Трата на основе чека` добавляет свойства:
- Фискальные данные чека (ФД, ФН, ФП)
- Место покупки
- Пользователь, добавивший чек
- Список товаров, если успешно обработано
- Состояние (Обрабатывается, Обработано, ошибка)
- Текст ошибки, если ошибка обработки
- Сумма береться либо из суммы 

`Товар` содержит:
- Название 
- Стоимость
- Количество
- Сумму

## Взаимодействие с приложением

На данный момент я работаю над SPA на Blazor wasm. 

### Пользовательские сценарии работы (с точки зрения UI)

#### Сценарий 1: Первый вход в систему (Новый пользователь)

**Экран регистрации:**
1. Пользователь открывает приложение и видит форму регистрации
2. Заполняет поля:
   - Логин (с проверкой доступности через `/api/login/exist`)
   - Полное имя
   - Пароль
   - Подтверждение пароля
3. При отправке формы вызывается `/api/register`
4. После успешной регистрации автоматически выполняется вход через `/api/login`
5. Пользователь перенаправляется на экран выбора бюджета

**Экран входа:**
1. Пользователь вводит логин и пароль
2. При отправке вызывается `/api/login`
3. Полученные токены сохраняются в локальном хранилище
4. Пользователь перенаправляется на главную страницу или экран выбора бюджета

#### Сценарий 2: Выбор и работа с бюджетом

**Экран списка бюджетов:**
1. Пользователь видит список всех своих бюджетов (загрузка через `/api/budgets`)
2. Для каждого бюджета отображается название
3. Кнопка "Создать новый бюджет" ведет на форму создания
4. При клике на бюджет происходит выбор и сохранение в состоянии приложения
5. После выбора пользователь перенаправляется на главную страницу

**Экран создания бюджета:**
1. Форма с полями:
   - Название бюджета
   - Лимит расходов (опционально)
   - День начала расчетного периода
2. При сохранении вызывается `POST /api/budgets`
3. После создания пользователь перенаправляется на список бюджетов
4. Новый бюджет автоматически выбирается для работы

**Экран деталей бюджета:**
1. Отображается информация о бюджете (загрузка через `GET /api/budgets/{id}`):
   - Название
   - Лимит расходов
   - День начала периода
2. Список участников бюджета (загрузка через `GET /api/budgets/{id}/users`):
   - Имя пользователя
   - Роль в бюджете
3. Кнопки действий (в зависимости от прав, полученных через `GET /api/budgets/{id}/permissions`):
   - "Редактировать" (если есть право на редактирование)
   - "Удалить" (если есть право на удаление)
   - "Добавить пользователя" (если есть право на редактирование)

**Экран редактирования бюджета:**
1. Форма с предзаполненными данными бюджета
2. Пользователь может изменить название, лимит и день начала периода
3. При сохранении вызывается `PUT /api/budgets/{id}`
4. После сохранения возврат на экран деталей бюджета

**Экран управления пользователями бюджета:**
1. Список текущих участников с их ролями
2. Форма добавления нового пользователя:
   - Поиск пользователя по логину или ID
   - Выбор роли из доступных ролей
   - При сохранении вызывается `POST /api/budgets/{id}/users`
3. Для каждого пользователя кнопка "Удалить" (кроме владельца)
4. При удалении вызывается `DELETE /api/budgets/{id}/users/{userId}`

#### Сценарий 3: Учет трат

**Экран списка трат:**
1. Отображается список всех трат выбранного бюджета (загрузка через `GET /api/budgets/{id}/spendings`)
2. Для каждой траты отображается:
   - Описание
   - Сумма
   - Дата покупки
   - Категория (если указана)
3. Возможность фильтрации и сортировки трат
4. Кнопка "Добавить трату" ведет на форму добавления

**Экран добавления траты вручную:**
1. Форма с полями:
   - Сумма (обязательно)
   - Описание (обязательно)
   - Дата покупки (Обязательно)
   - Сумма (Обязательно)
   - Категория (опционально, выбор из дерева категорий через `GET /api/categories/tree`)
2. При сохранении вызывается `POST /api/budgets/{id}/spendings/manual`
3. После сохранения возврат на список трат с обновленными данными

**Экран добавления чека:**
1. Два режима ввода:
   - **Ввод вручную:** форма с полями:
     - Фискальные данные (ФД, ФН, ФП)
     - Сумма
     - Дата покупки
   - **Загрузка файла:** поле для загрузки файла с данными чека
2. Переключение между режимами кнопкой
3. Если чека с этими данными (ФД, ФН, ФП) еще не было добавлено, он добавляется со статусом "Обрабатывается".

***После предварительного добавления чека в фоновом процессе выполняется следушее:***
1. Данные чека передаются в ФНС.
    - Если данные обработаны успешно, то трате добавляется список продуктов и устанавливается статус "Обработано"
    - Если произошла ошибка, требующая повторного запроса через некоторое время (слишком много запросов, данные чека еще не получены и т.п.), статус траты остается "Обрабатывается", устанавливается время следующей попытки NextRetryAt и RetryCount увеличивается на 1.
    - Если произошла ошибка, не требующая повторного запроса, то устанавливается статус "Ошибка" и сохраняется текст ошибки
2. В будушем, после получения продуктов еще будет происходить категоризация.

**Экран списка чеков:**
1. Список всех чеков, добавленных в бюджет
2. Для каждого чека отображается:
   - Место покупки
   - Дата покупки
   - Сумма
   - Статус обработки (Обрабатывается/Обработано/Ошибка)
   - Список товаров (если обработано)
3. Сортировка по дате покупки
4. При клике на чек - просмотр деталей

#### Сценарий 4: Работа с категориями

**Экран выбора категории:**
1. Древовидная структура категорий (загрузка через `GET /api/categories/tree`)
2. Возможность раскрывать/сворачивать узлы дерева
3. Выбор категории для траты
4. Поиск категории по названию

**Экран списка категорий:**
1. Список категорий с возможностью фильтрации по родительской категории (загрузка через `GET /api/categories?parentId={id}`)
2. Отображение иерархии категорий
3. Индикация наличия дочерних категорий

#### Сценарий 5: Управление профилем

**Экран профиля пользователя:**
1. Отображение информации о текущем пользователе (загрузка через `GET /api/users/{id}`):
   - Логин
   - Полное имя
   - Дата регистрации
2. Кнопка "Редактировать" ведет на форму редактирования

**Экран редактирования профиля:**
1. Форма с полями:
   - Логин (можно изменить)
   - Полное имя (можно изменить)
2. При сохранении вызывается `PUT /api/users/{id}`
3. После сохранения возврат на экран профиля

#### Сценарий 6: Обновление токена доступа

**Автоматический процесс:**
1. При истечении JWT токена автоматически вызывается `POST /api/refresh`
2. Новые токены сохраняются в локальном хранилище
3. Пользователь продолжает работу без прерывания
4. При неудачном обновлении токена - перенаправление на экран входа

#### Сценарий 7: Навигация и главная страница

**Главная страница:**
1. Приветствие с названием выбранного бюджета
2. Меню доступных функций:
   - Добавление чека
   - Список чеков
   - Список трат
   - Детали бюджета
   - Управление пользователями (если есть права)
3. Краткая статистика по бюджету (если реализована)
4. Если бюджет не выбран - автоматический редирект на экран выбора бюджета

**Общие элементы UI:**
- Шапка с названием приложения
- Индикатор выбранного бюджета
- Кнопка выхода из системы
- Навигационное меню
- Уведомления об успешных операциях и ошибках
