# ADR-0001: Модульный монолит в одном csproj

## Статус

Accepted

## Контекст

Проект HomeAccounting начинался как модульный монолит с разделением на отдельные csproj по bounded context'ам (отдельные проекты для Budgets, Users, Categories и т.д.). Это привело к следующим проблемам:

- Сложность управления зависимостями между проектами.
- Трудности с разделением на слои и определением границ bounded context'ов.
- Overhead от инфраструктуры множества проектов при небольшом размере кода.

В качестве референса был изучен [evolutionary-architecture-by-example](https://github.com/evolutionary-architecture/evolutionary-architecture-by-example), в частности Chapter 1, где демонстрируется подход «один проект с модулями через неймспейсы».

## Варианты

1. **Микросервисы** — отдельные сервисы для каждого bounded context. Слишком много инфраструктурного overhead для одного разработчика и текущего масштаба проекта.
2. **Множество csproj** — текущий подход с разделением на проекты. Уже показал себя проблемным.
3. **Один csproj с неймспейсами** — все модули в одном проекте, разделение через неймспейсы и конвенции.

## Решение

Весь бэкенд собран в один csproj `HomeAccounting` с организацией по bounded context'ам через неймспейсы:

- `HomeAccounting.Budgets`
- `HomeAccounting.Users`
- `HomeAccounting.Categories`
- `HomeAccounting.ReceiptProcessing`
- `HomeAccounting.Products`
- `HomeAccounting.Common`

Границы между модулями поддерживаются через конвенции: модули не ссылаются друг на друга напрямую по доменной логике, общее — в `Common`, пересечение — через интерфейсы.

## Последствия

**Положительные:**
- Проще управлять зависимостями — один проект, один граф.
- Меньше инфраструктурного кода.
- Быстрее компиляция и запуск.
- При необходимости можно вынести модуль в отдельный проект или сервис позже.

**Отрицательные:**
- Границы модулей поддерживаются только конвенциями, а не компилятором.
- Требуется дисциплина при добавлении зависимостей между модулями.
- Старые проекты от предыдущего подхода ещё не удалены (legacy).
